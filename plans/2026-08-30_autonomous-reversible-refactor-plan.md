# Autonomous Reversible Refactor Plan for PyTAAA

## Goal

Refactor the PyTAAA codebase for clarity, organization, maintainability, and more efficient execution without changing the trading behavior or output materially. The refactor must be reversible, test-driven, and governed by an autonomous validation loop that rejects any change that shifts backtest values, stock selections, or weights beyond the allowed tolerance.

## Working principles

1. Preserve behavior first; refactor second.
2. Keep each change small and easy to revert.
3. Validate against real production entry points and real configuration files.
4. Commit only after a passing validation cycle.
5. If validation fails, revert the last refactor and record why it failed.
6. Prefer readability and encapsulation without altering algorithmic outputs.

## Required behavior to preserve

The refactor must preserve the same feature set and runtime behavior as the current repo, especially for:

- the five primary JSON-backed portfolio models in `pytaaa_main.py`
- `daily_abacus_update.py`
- `recommend_model.py`
- the web update workflow triggered by `run_pytaaa_daily.sh`
- existing stock universe selections and monthly weights

The refactor must not change the logic that determines:

- which stock universe is selected each month
- the selected stocks for the last 3 months
- the portfolio weights within tolerance
- the final backtest values for the benchmark production flows

## Acceptance thresholds

These are the acceptance guardrails for any refactor step:

- Backtest final values must remain within +/- 2% of the current baseline values.
- Monthly stock selections must remain the same for the recent 3-month window.
- Portfolio weights must remain approximately the same; target tolerance is +/- 5% relative to the original weights.
- CLI usage and JSON config compatibility must remain unchanged.
- The README and user-facing docs must be updated to reflect any actual refactor changes.
- The refactor must happen on a dedicated branch and remain easy to undo.

## Branch strategy

Create a new branch before any code refactor begins:

```bash
git checkout -b refactor/reversible-readability-2026-08-30
```

This branch should be the only branch used for this work. All refactor changes must be committed in small increments so they can be rolled back individually.

## Proposed refactor scope

The refactor should focus on the flow that is already working, not on speculative rewrites. The likely safe candidate areas are:

- `pytaaa_main.py` for orchestration clarity
- `run_pytaaa.py` for the production pipeline structure
- `functions/` modules for helper extraction and naming cleanup
- `recommend_model.py` for clearer modular design without changing logic
- `daily_abacus_update.py` for CLI and orchestration clarity
- docs and README for current usage parity

Avoid large rewrite efforts in the statistical backtesting core unless a small, behavior-preserving extraction is required.

## Autonomous work loop

The refactor must be executed by a closed, autonomous loop rather than by a manual chat-side approval gate. The loop is responsible for all of the following without requiring intervention from the user:

1. Detect whether the production baseline gate is already running.
2. If it is still running, wait until it finishes before evaluating the state.
3. If no completed verdict exists, execute the production gate automatically.
4. If the gate passes, continue to the next refactor step.
5. If the gate fails, revert the last refactor change automatically and stop the current iteration.
6. Repeat until the work is complete and all gates pass.

This flow is encoded in `scripts/continue_refactor_decision.py` and is designed to replace the previous chat-driven "please intervene" behavior with an automated wait/run/revert cycle. The controller is authoritative for loop progression; it no longer expects a human to tell it whether to continue, wait, or revert.

### Required autonomous behavior

For every loop iteration, the controller must do the following automatically:

- keep polling for any active production gate process
- wait on the gate if a prior run is still in progress
- run the gate automatically when the log is absent, incomplete, or belongs to
	a different commit
- parse the final gate verdict from the log
- proceed immediately when the verdict is PASS
- record the candidate commit SHA with the gate output
- revert that exact candidate with `git revert` when the verdict is FAIL
- never use a stale verdict to revert another commit
- never use `git reset HEAD~1` or force-push as an automatic failure action
- stop only when the state is resolved or the wait limit is reached

### Autonomous verification checklist

For every loop iteration, validate:

- `pytaaa_main.py` still runs for the five JSON configs
- `recommend_model.py` still runs for the abacus config
- `daily_abacus_update.py` still runs for the abacus config
- `run_pytaaa_daily.sh` still produces the same stock universe and weights for the recent 3 months
- final values are within allowed tolerance
- documentation is still correct for the user-facing commands

## Refactor phases

### Phase 1: Stabilize and baseline

Tasks:

- create the refactor branch
- capture the true baseline outputs in `.refactor_baseline/before`
- verify the current command set and outputs
- record the exact stock selections and final values for the current working state

Definition of done:

- baseline exists
- all validation commands are documented
- no refactor code has been changed yet

### Phase 2: Low-risk readability cleanup

Target areas:

- pure naming cleanup
- docstrings
- dead code removal that has no runtime effect
- extraction of helper methods without changing logic

Constraints:

- keep algorithmic behavior identical
- avoid changing model selection or ranking logic during this phase

Definition of done:

- small, reviewable commit(s)
- validation within tolerance
- logs still match baseline summary

### Phase 3: Object-oriented and modular cleanup

Refactor only the benign orchestration layer:

- package helper logic into small classes/functions
- reduce duplicate code paths
- clarify responsibilities without changing data flow

Avoid touching:

- critical Monte Carlo optimization code
- ranking logic
- final portfolio calculation logic
- monthly stock-selection rules

Definition of done:

- same outputs within tolerance
- CLI entry points unchanged
- module boundaries are cleaner but behavior is equivalent

### Phase 4: Performance and execution efficiency

Apply safe optimization only after correctness is proven:

- reduce repeated computations where output is unchanged
- cache safe, pure, repeated data reads if the functional behavior is preserved
- simplify loops without altering trading semantics

Definition of done:

- no output drift beyond allowed tolerance
- runtime improves or remains equivalent
- doc summaries updated

### Phase 5: Documentation and handoff

Tasks:

- update README and user guidance
- add a short refactor note in docs explaining the new structure
- confirm all commands still work as before
- ensure a new user can use the same workflow without hidden changes

Definition of done:

- docs and README are accurate
- command examples are current
- workflow remains reproducible from a clean repo state

## Required comparison method

A refactor is accepted only when the current run remains within the allowed tolerances against the pre-refactor baseline.

### Compare required outputs

1. Backtest final values from the main pytaaa_main.py workflows
2. Backtest final values from the abacus update flows
3. Selected stocks for the recent 3-month window
4. Portfolio weights and ranking order
5. Log summaries and generated outputs

### Suggested comparison logic

- For backtest final values: compare before/after percentages and ensure delta <= 2%
- For weights: compare each position and ensure approximate parity within +/- 5%
- For stock selection: ensure the selected symbols remain identical over the last 3 months
- For CLI flags and JSON files: no breaking changes allowed

## Revert and retry strategy

When a refactor fails the validation loop:

```bash
git status
git diff

# revert the last refactor commit
git reset --soft HEAD~1

# or if needed, revert a specific file
git restore --source=HEAD -- path/to/file.py
```

If a candidate refactor cannot be made safe without drifting away from the baseline, stop work on that path and either simplify the change or revert it entirely.

## Exit criteria

The refactor is complete only when all of the following are true:

- work is on the dedicated refactor branch
- each refactor step is committed in small reversible units
- all critical flows still pass under the real production command set
- stock selections are unchanged for the recent 3-month period
- portfolio weights remain within the allowed approx tolerance
- final backtest values remain within +/- 2% of baseline
- relevant docs are updated and accurate
- a new user can reproduce the workflow without surprise behavior changes

## Final deliverable

This plan should be used as the operating guide for autonomous refactoring. The agent should treat it as a runtime contract: refactor only when the validation loop remains green, and revert immediately whenever the output drift exceeds the allowed tolerance.
